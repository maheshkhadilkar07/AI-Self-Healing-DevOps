Literature Survey

Existing work covers pieces of the problem (DevSecOps, MLOps, auto-scaling, defect prediction, CI/CD reliability) but none combines detection, root-cause analysis, safe automated recovery and verification — the gap this project fills.

YearPaperMethodologyKey findingsResearch gap
2024Identifying the primary dimensions of DevSecOps: A multi-vocal literature reviewStudies information from different DevSecOps sources to identify its major areas and practices.Highlights the importance of including security throughout development and operations.Discusses DevSecOps practices but has no AI-based self-healing mechanism for application failures.
2025An analysis of the challenges in the adoption of MLOpsExamines technical and practical problems involved in adopting MLOps.Putting ML into production involves challenges with tools, processes, people and system management.Discusses MLOps challenges but gives no complete system for automatic failure detection and recovery.
2025Towards resource-efficient reactive and proactive auto-scaling for microservice architecturesLooks at reactive and proactive scaling methods that adjust resources to application needs.Better scaling maintains performance while avoiding unnecessary resource usage.Scaling is only one recovery action; not combined with anomaly detection and root-cause analysis.
2025Gwydion: Efficient auto-scaling for complex containerized applications in Kubernetes through reinforcement learningUses reinforcement learning to make scaling decisions for containerized applications on Kubernetes.Can improve resource usage and performance compared with basic scaling methods.Focuses on auto-scaling; other failure types and recovery actions are not handled in the same system.
2025Industrial applications of artificial intelligence in software defects prediction: Systematic review, challenges, and future worksReviews how AI techniques predict software defects in industrial settings.AI can help identify possible defects and improve the development process.Defect prediction happens during development; it does not solve failures after deployment.
2026Just-in-time bug classifier: A step towards integrating Automated Program Repair in CI/CD pipelinesUses bug classification to identify problems in CI/CD and decide whether automated repair applies.Bug classification helps select a suitable repair approach during development.Deals with software bugs and automated repair, not runtime failures and complete system recovery.
2026Early detection of emerging CI/CD reliability degradation through multi-source triangulation and deep representation learningCombines information from different sources and analyses it with deep learning to find reliability problems early.Multiple sources help identify signs of CI/CD degradation before they grow.Focuses on early detection; automatic root-cause analysis and recovery are not covered together.
2026Static validation for declarative service orchestration: Enabling reliable CI/CD and MLOps pipelinesChecks service configurations and dependencies before a workflow is executed.Early validation catches configuration problems before they affect deployment.Prevents errors before execution; does not handle unexpected runtime failures.
2026On the use of machine learning for failure prediction after collective changes in automated continuous integration testingUses ML to study software changes and predict whether they may fail in automated CI testing.ML can identify changes that are more likely to cause failures.Predicts failures in CI testing rather than detecting and recovering from live application failures.
2026Performance optimization model for predicting the impact of refactorings in CI/CD pipelinesA prediction model estimates how refactoring may affect CI/CD performance.Helps developers understand the performance effect before making changes.Deals with performance prediction; no automated failure recovery.

How this project closes the gap

One closed loop covers detect → diagnose → decide → heal → verify → learn for failures that occur after deployment, using several recovery actions (restart, scale, rollback) under a safety policy. See the methodology and the live architecture.
